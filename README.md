# w10-toolbox

小工具集合。

## color-transition-preview.html — 专辑取色 & 过渡插值预览

参考 Spotify 等音乐 App 的「从封面提取主色作为背景 + 切歌时背景平滑过渡」设计,用来**验证不同颜色插值算法**的小工具。

### 功能

- 从 `img/` 下的图片用 **Median Cut** 提取主色(可选 鲜艳 Vibrant / 主色 Dominant)
- 圆形轮播:滚轮 / 拖拽 / ← → 切换图片
- 切换时背景在多种色彩空间做插值过渡,可实时切换:
  - `sRGB 直插`(基线,发脏)
  - `gamma-linear`(线性光插值,**嵌入式推荐**)
  - `HSL` / `CIELAB` / `OKLab`(最优)
- **分屏对比**两种算法、**纯色 / 渐变**背景切换、可调**时长**与**缓动**
- 每次切换从「当前显示色」重定向出发,插入 / 快速连切都平滑不跳变

### 使用

直接双击 `color-transition-preview.html` 打开即可(图片已 base64 内联进 `img-data.js`,无需起服务器,也绕开 `file://` 下 canvas 读像素被污染的问题)。

滚轮 / 拖拽 / ← → 切换图片,右上角面板调参对比。

## fortune_sticks/fortune-sticks.html — 摇签筒动画(水墨手绘 / 2 秒无缝循环)& 视频 / 图片导出

2D Canvas 手绘水墨风摇动签筒动画:深色氛围底 + 中心暖光晕 + 深红木质签筒(金色顶底环 + 木纹笔触)+ 上方向外散开摇晃的竹签,配合柔和光晕投影和飘散的光雾。整个动画数学上完全首尾闭合(所有时变量都用 `sin(2π·phase)` / `cos(2π·phase)` 构造),无缝循环 2 秒。风格参考现代二次元游戏 UI(如 stick.mp4)的过场氛围。

### 功能

- **一键无缝循环 2 秒** 摇动过场,起止相位一致,导出的 `.webm` 首尾可直接拼接
- 可调:单周期时长、摇动幅度、竹签抖动烈度、光雾 / 运动线 / 星光粒子强度
- 点击画布或按 <kbd>空格</kbd> 暂停 / 恢复(暂停位置保留,不会跳变)
- **导出视频**(`canvas.captureStream` + `MediaRecorder`,`.webm`),恰好一个周期,默认 **480×832** 竖版
- **导出图片**(`canvas.toBlob`,`.png`),当前静态帧,尺寸 = 同一分辨率
- 分辨率预设:480×832 / 540×960 / 720×1280 / 480² / 720²

### 使用

直接双击 `fortune_sticks/fortune-sticks.html` 打开即可,无需服务器(离线可用)。导出录制建议用 Chrome / Edge。

## coin_flip/coin-flip.html — 抛硬币动画(3D)& 视频 / 图片导出俯视白底视角的 **3D** 抛硬币动画:正面 **YES** / 反面 **NO**,点击后硬币向上跳起、边翻转边自转靠近相机(真实透视放大),再落回平面并带小回弹。硬币为**任天堂金币卡通风**(车削圆润厚边 + 扁平明亮卡通金 + 粗圆角描边字 + 干净单内圈,同金色不用字色),配方向光与柔和阴影。可一键**导出视频**或**静态落地 PNG 图片**。

### 功能

- 点击画布 / 按 <kbd>空格</kbd> 抛掷,结果随机(YES / NO 各 50%,自动对齐落地朝上的面)
- 可调**时长**、**翻转圈数**、**靠近程度**(峰值透视放大倍率)、**俯视角**
- **导出视频**(`canvas.captureStream` + `MediaRecorder`,`.webm`),从硬币腾空瞬间开始录制,分辨率 = 面板设置,默认 **360×360**,含常用预设(方形 / 竖屏)
- **导出图片**(`canvas.toBlob`,`.png`),导出当前**静态落地帧**,白底,尺寸 = 同一分辨率设置
- 真 3D:Three.js(r128,UMD)已内置于 `coin_flip/lib/`,无需联网

### 使用

直接双击 `coin_flip/coin-flip.html` 打开即可,无需服务器(离线可用)。导出录制建议用 Chrome / Edge。

## camera_preview/camera-preview.html — Camera dump 裸数据预览

把 camera 模块 dump 出来的**裸图像数据**按指定格式 / 尺寸还原成图像。调 sensor、ISP、V4L2 链路时最常见的场景:手里一个 `.raw` / `.yuv`,只知道大概是什么格式,想快点看到画面对不对。纯本地运行(File API),文件不上传、不落盘。

### 支持格式(26 种)

| 组 | 格式 |
|---|---|
| RGB | `RGB565` `BGR565` `RGB888` `BGR888` `RGBA8888` `BGRA8888` |
| YUV422 | packed `YUYV` `YVYU` `UYVY` `VYUY` · semi-planar `NV16` `NV61` · planar `I422` `YV16` |
| YUV420 | `NV12` `NV21` `I420` `YV12` |
| GRAY | `GRAY8` |
| RAW Bayer | `RAW8` · `RAW10` / `RAW12`(**MIPI CSI-2 packed** 与 unpacked 两种)· `RAW16` |
| 压缩 | `JPEG` / MJPEG 单帧(走浏览器 `createImageBitmap`) |

### 功能

- **尺寸**:38 个常用分辨率下拉(QQVGA→8K、手机常见 4:3 / 16:9 / sensor 全尺寸),也可直接手输宽高
- **按文件大小推断尺寸**:由格式的平均 bpp 反解候选,常见分辨率和长宽比吻合的排前面,点一下即用
- **行跨距 stride**:DMA / V4L2 buffer 常按 16/32/64/128/256 字节对齐,「对齐」按钮循环套用常见值;推断尺寸时会优先给「恰好填满该 stride」的宽度
- **文件名自动识别**:`nv12_4032_3024.yuv`、`raw10p_rggb_1920x1080.raw`、`rgb565_stride1344_640x480.raw` 这类命名可自动定出格式 / 尺寸 / stride / CFA / 矩阵 / 字节序
- **YUV 参数**:limited(16–235)/ full range,BT.601 / BT.709 / BT.2020 矩阵
- **RAW 参数**:CFA 排列 `RGGB/BGGR/GRBG/GBRG` + `mono`(不去马赛克,直接看 Bayer 网格)、黑 / 白电平(自动或手填)、gamma、R/G/B 增益、灰世界白平衡
- **字节序 / 对齐**:16bit 格式的大小端、LSB / MSB 对齐
- **数据偏移**:跳过文件头部(`offset`),dump 带 header 时不用另外裁文件
- **读数**:鼠标悬停给出坐标、RGB / HEX、以及**该像素在源文件里的字节偏移**(对着 hex 编辑器核对用);11×11 放大镜;≥8× 时叠像素网格并用粗线标出 Bayer 2×2 边界
- 直方图(98% 分位压峰)、通道单看 R/G/B/灰度、暗部 / 高光截断比例、「整帧同值」警告(格式或尺寸选错的典型征兆)
- 多文件拖入后 <kbd>[</kbd> <kbd>]</kbd> 翻帧(每帧按自己的文件名重新识别格式);导出 PNG / 复制到剪贴板

### 使用

直接双击 `camera_preview/camera-preview.html`,把 dump 文件拖进去即可,无需服务器。

### 自测

解码逻辑全部在 `decoders.js`(UMD,不碰 DOM),所以能在 Node 里跑 ground-truth 回归:

```bash
cd camera_preview
python make_samples.py      # 需要 pillow / numpy;生成 samples/ 下 32 个样例 + 基准图
node selftest.js
```

`make_samples.py` 先画一张参考图(彩条 / 灰阶 / 肤色渐变 / 1px 高频细纹),再编码成各种格式;`selftest.js` 解回来与 `reference.rgb` 逐像素比 maxErr / PSNR。实测 **43/43 全绿**:像素解码 31、跨格式一致性 4、尺寸推断 8。

两点关于阈值的说明,避免被误读成"放水":

- **RGB565 的 maxErr 7 是紧界**。编码端是截断(`v>>3`)而非四舍五入,误差上界就是步长−1 = 7(G 通道 3),实测正好 7/3/7。位展开必须用高位补低位(`(v<<3)|(v>>2)`);若图省事写成单纯左移,白色只能到 248,maxErr 立刻破 7。
- **RAW 只在 y<390 判定**。参考图最下面 1/4 是 1px 宽的黑白 / 红蓝细纹,而 Bayer 每个位置只有一个通道的样本 —— 采样率不足,任何去马赛克算法都还原不出来,这是物理限制不是 bug。平坦区实测 maxErr 160~176 / PSNR 29.2~29.4,峰值全部落在彩条硬边界 0~1px 内(双线性跨阶跃必然过冲),边界之外逐像素精确。

**跨格式一致性**是最强的正确性证据:同一画面编成 YUYV/YVYU/UYVY/VYUY 四种排列、planar 与 semi-planar、YUYV 与 NV16,解出来必须**逐位相同** —— 排列偏移或色度上采样写错一处就会立刻暴露。

## progressiveJpeg/ — Progressive JPEG 首扫 vs 高斯模糊 对比

把 PNG 转成 **progressive JPEG**,解出它**第一段扫描**(只有 DC 系数)的画面,和原图做**高斯模糊**的结果并排比较 —— 用来回答「渐进加载时那张先出来的糊图,和直接上高斯模糊占位图,差在哪」。

结论(466×466 样图,q85 4:2:0):首扫只用 **4.2 KB / 7.7%** 的字节就给出 **19.77 dB / SSIM 0.567**;要让高斯模糊糊到同样的失真量,需要 **σ≈4.3**,而那需要整张图 **413 KB** 全部下载完。首扫的糊是**逐块保真**的(每 8×8 一个平均色,亮度轮廓、明暗、色彩分布都在位),高斯模糊则是**无差别抹平**,亮部会往暗部渗。

### 功能

- `make_progressive.py`:编码 progressive JPEG,解析 `SOF2` / 每段 `SOS` 的 `Ss/Se/Ah/Al`,按扫描边界**截断 + 补 EOI** 得到 10 张「只收到前 N 段」的合法 JPEG 并逐个解码
- 首扫给两个版本:**带 DC 平滑**(libjpeg / 浏览器真实所见)与**无平滑**(ffmpeg,能看到 DC 系数原本的 8×8 色块)
- 用 PSNR / SSIM 反解**等效高斯 σ**:最像首扫的 σ(像素 / 结构两种口径)、与首扫失真等量的 σ,并给出理论参考(盒式滤波 σ=w/√12)
- `progressive-jpeg-compare.html`:交互查看器,拖扫描段 / 拖 σ、并排或**分屏拖动**对比、差异热力图、按住 <kbd>空格</kbd> 看原图、一键导出三联对比 PNG
- 查看器里的 PSNR / SSIM 由 JS 独立算一遍(SSIM 用标准 11×11 高斯窗 σ=1.5),与 Python 的 `metrics.json` **逐位对得上**,互为验证

### 使用

```bash
cd progressiveJpeg
python make_progressive.py            # 需要 pillow / numpy / scipy / scikit-image;ffmpeg 可选
```

产物在 `out/`:`comparison.png`(六格总览)、`scan_stages.png`(10 段渐进过程)、`blur_stages.png`(σ 阶梯)、`metrics.json`、以及查看器用的 `data.js`。

跑完直接双击 `progressive-jpeg-compare.html`(图片已 base64 内联进 `data.js`,`file://` 下也能读 canvas 像素,无需起服务器)。换图:`python make_progressive.py --src 你的图.png -q 90`。

## progressiveJpeg/ — 双表法毛玻璃(嵌入式大 σ 近似)

`make_frostglass.py`。常规做法是拿大核卷积换 σ,这里反过来:**让 σ 从采样几何里免费长出来**。

```
JPEG scale=1/8 解码 = 每 8×8 块只取 DC = 宽 8 的 box    方差 (8²−1)/12 = 5.25
双线性上采样 8×     = 半宽 8 的三角核                  方差 8²/6     = 10.67
两者独立,方差相加  ->  σ_base = √15.92 = 3.99         一次卷积都没做
```

再在 59×59 的小图上叠 n 趟 w×w 的 box(小图 1 px 折算原图 8 px,方差按 64 倍放大),σ 可以推到任意大:`σ_total = √(16 + (64/12)·n·(w²−1))`。

**「双表」**指编码和解码用两张不同的量化表 —— 编码用 `Q_enc`(AC=255,把 AC 系数全量化成 0),写进文件的 `Q_dec` 则是 AC=1。两份码流的熵数据**逐位相同**,只有 DQT 那 126 字节不同,改表不需要重新编码。

### 实测(466×466 样图,Q(0,0)=8/16,4:2:0)

码流 **6,171 B**(bpp 0.227),是普通 q75 的 **0.142×**;折算 640×480 约 **8.5 KB**。

| 管线 | 公式 σ | 实测 σ | vs 真高斯 PSNR | SSIM |
|---|---|---|---|---|
| 1/8 + 双线性(无后处理) | 4.00 | **5.5** | 24.70 dB | 0.845 |
| + box(3)×1 · 常规毛玻璃 | 7.66 | **8.9** | 29.90 dB | 0.966 |
| + box(3)×3 · iOS 风格 | 12.00 | **12.7** | 33.22 dB | 0.990 |
| + box(5)×3 · CSS blur(20px) | 20.00 | **20.8** | 37.27 dB | 0.995 |
| + box(7)×3 · 极重虚化 | 28.00 | **29.1** | 40.00 dB | 0.996 |

σ≥8.9 起与真高斯**肉眼无法分辨**(SSIM ≥0.966),而真高斯需要全部 636 KB 像素在手。公式只叠了小图上的 box、漏掉上采样 tent 的贡献,所以**系统性低估 0.6~1.5**;要精确对齐 CSS `blur(Npx)` 请查「实测 σ」列,别直接用公式。

### 三个容易踩的坑(`failure_modes.png` 里有图)

- **单表法**(把 AC=255 留在文件里):一旦被 1/1 全解码就是振铃,与双表版最大差 **190 灰阶**
- **不改表**(`Q_dec` = `Q_enc`):1/8 下仍残留 **52 灰阶**,分通道看 `Y=0 / Cb=30 / Cr=30` —— 4:2:0 时色度 `_DCT_scaled_size` 被抬到 2,走 `jpeg_idct_2x2` 会吃低频 AC。所以**「表整形在 1/8 路径下无效」只对亮度成立**,`Q_dec` AC=1 在 4:2:0 下不是保险而是必需项
- **Q(0,0) 两表不一致**:增益 r 使 `像素 → 128 + r·(像素−128)`,是**围绕 128 的对比度缩放**而非亮度偏移。r=2 饱和 30.1%,r=4 饱和 48.5%,双向削波不可逆

### 平移不变性(方案外的发现)

box 的采样格点钉死在 8 的倍数上,平移不会被吸收。内容相对网格平移 0~7 px、对齐后比残差:

| 档位 | 双表 最大 / 平均 | 真高斯 最大 / 平均 |
|---|---|---|
| 1/8 + 双线性 | **100.0** / 5.06 | 29.0 / 0.03 |
| + box(3)×3 | 29.0 / 0.90 | 24.0 / 0.13 |
| + box(7)×3 | 19.0 / 0.76 | 18.0 / 0.32 |

静态壁纸无所谓;**滚动 / 摄像头场景会看到「呼吸感」**,σ 越大越轻(box 叠得多就越接近平移不变)。

### 使用

```bash
cd progressiveJpeg
python make_frostglass.py                 # 跑全部预设档位
python make_frostglass.py --sigma 15      # 反解 (w,n) 命中目标 σ
python make_frostglass.py --q00 4 8       # 换 DC 量化步长
```

产物在 `out_frost/`:`overview.png`(管线四步)、`frost_vs_gauss.png`(五档位左右对照真高斯)、`failure_modes.png`(四种踩坑)、`metrics.json`、以及查看器用的 `data.js`。

### 交互查看器

跑完直接双击 `frostglass-compare.html`。拖 `w` / `n` 滑块实时看效果,右边自动跟到最匹配的真高斯 σ 做对照。

- 五个预设档位一键切换,<kbd>←</kbd><kbd>→</kbd> 也能切
