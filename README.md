# w10-toolbox

小工具集合。

## color-transition-preview.html — 专辑取色 & 过渡插值预览

参考 Spotify 等音乐 App 的「从封面提取主色作为背景 + 切歌时背景平滑过渡」设计,用来**验证不同颜色插值算法**的小工具。

### 功能

- 从 `img/` 下的图片用 **Median Cut** 提取主色(可选 鲜艳 Vibrant / 主色 Dominant)
- 圆形轮播:滚轮 / 拖拽 / ← → 切换图片
- 切换时背景在多种色彩空间做插值过渡,可实时切换:
  - `sRGB 直插`(基线,发脏)
  - `gamma-linear`(线性光插值,**嵌入式推荐**)
  - `HSL` / `CIELAB` / `OKLab`(最优)
- **分屏对比**两种算法、**纯色 / 渐变**背景切换、可调**时长**与**缓动**
- 每次切换从「当前显示色」重定向出发,插入 / 快速连切都平滑不跳变

### 使用

直接双击 `color-transition-preview.html` 打开即可(图片已 base64 内联进 `img-data.js`,无需起服务器,也绕开 `file://` 下 canvas 读像素被污染的问题)。

滚轮 / 拖拽 / ← → 切换图片,右上角面板调参对比。

## fortune_sticks/fortune-sticks.html — 摇签筒动画(水墨手绘 / 2 秒无缝循环)& 视频 / 图片导出

2D Canvas 手绘水墨风摇动签筒动画:深色氛围底 + 中心暖光晕 + 深红木质签筒(金色顶底环 + 木纹笔触)+ 上方向外散开摇晃的竹签,配合柔和光晕投影和飘散的光雾。整个动画数学上完全首尾闭合(所有时变量都用 `sin(2π·phase)` / `cos(2π·phase)` 构造),无缝循环 2 秒。风格参考现代二次元游戏 UI(如 stick.mp4)的过场氛围。

### 功能

- **一键无缝循环 2 秒** 摇动过场,起止相位一致,导出的 `.webm` 首尾可直接拼接
- 可调:单周期时长、摇动幅度、竹签抖动烈度、光雾 / 运动线 / 星光粒子强度
- 点击画布或按 <kbd>空格</kbd> 暂停 / 恢复(暂停位置保留,不会跳变)
- **导出视频**(`canvas.captureStream` + `MediaRecorder`,`.webm`),恰好一个周期,默认 **480×832** 竖版
- **导出图片**(`canvas.toBlob`,`.png`),当前静态帧,尺寸 = 同一分辨率
- 分辨率预设:480×832 / 540×960 / 720×1280 / 480² / 720²

### 使用

直接双击 `fortune_sticks/fortune-sticks.html` 打开即可,无需服务器(离线可用)。导出录制建议用 Chrome / Edge。

## camera_preview/camera-preview.html — Camera dump 裸数据预览

把 camera 模块 dump 出来的**裸图像数据**按指定格式 / 尺寸还原成图像。调 sensor、ISP、V4L2 链路时最常见的场景:手里一个 `.raw` / `.yuv`,只知道大概是什么格式,想快点看到画面对不对。纯本地运行(File API),文件不上传、不落盘。

### 支持格式(26 种)

| 组 | 格式 |
|---|---|
| RGB | `RGB565` `BGR565` `RGB888` `BGR888` `RGBA8888` `BGRA8888` |
| YUV422 | packed `YUYV` `YVYU` `UYVY` `VYUY` · semi-planar `NV16` `NV61` · planar `I422` `YV16` |
| YUV420 | `NV12` `NV21` `I420` `YV12` |
| GRAY | `GRAY8` |
| RAW Bayer | `RAW8` · `RAW10` / `RAW12`(**MIPI CSI-2 packed** 与 unpacked 两种)· `RAW16` |
| 压缩 | `JPEG` / MJPEG 单帧(走浏览器 `createImageBitmap`) |

### 功能

- **尺寸**:38 个常用分辨率下拉(QQVGA→8K、手机常见 4:3 / 16:9 / sensor 全尺寸),也可直接手输宽高
- **按文件大小推断尺寸**:由格式的平均 bpp 反解候选,常见分辨率和长宽比吻合的排前面,点一下即用
- **行跨距 stride**:DMA / V4L2 buffer 常按 16/32/64/128/256 字节对齐,「对齐」按钮循环套用常见值;推断尺寸时会优先给「恰好填满该 stride」的宽度
- **文件名自动识别**:`nv12_4032_3024.yuv`、`raw10p_rggb_1920x1080.raw`、`rgb565_stride1344_640x480.raw` 这类命名可自动定出格式 / 尺寸 / stride / CFA / 矩阵 / 字节序
- **YUV 参数**:limited(16–235)/ full range,BT.601 / BT.709 / BT.2020 矩阵
- **RAW 参数**:CFA 排列 `RGGB/BGGR/GRBG/GBRG` + `mono`(不去马赛克,直接看 Bayer 网格)、黑 / 白电平(自动或手填)、gamma、R/G/B 增益、灰世界白平衡
- **字节序 / 对齐**:16bit 格式的大小端、LSB / MSB 对齐
- **数据偏移**:跳过文件头部(`offset`),dump 带 header 时不用另外裁文件
- **读数**:鼠标悬停给出坐标、RGB / HEX、以及**该像素在源文件里的字节偏移**(对着 hex 编辑器核对用);11×11 放大镜;≥8× 时叠像素网格并用粗线标出 Bayer 2×2 边界
- 直方图(98% 分位压峰)、通道单看 R/G/B/灰度、暗部 / 高光截断比例、「整帧同值」警告(格式或尺寸选错的典型征兆)
- 多文件拖入后 <kbd>[</kbd> <kbd>]</kbd> 翻帧(每帧按自己的文件名重新识别格式);导出 PNG / 复制到剪贴板

### 使用

直接双击 `camera_preview/camera-preview.html`,把 dump 文件拖进去即可,无需服务器。

### 自测

解码逻辑全部在 `decoders.js`(UMD,不碰 DOM),所以能在 Node 里跑 ground-truth 回归:

```bash
cd camera_preview
python make_samples.py      # 需要 pillow / numpy;生成 samples/ 下 32 个样例 + 基准图
node selftest.js
```

`make_samples.py` 先画一张参考图(彩条 / 灰阶 / 肤色渐变 / 1px 高频细纹),再编码成各种格式;`selftest.js` 解回来与 `reference.rgb` 逐像素比 maxErr / PSNR。实测 **43/43 全绿**:像素解码 31、跨格式一致性 4、尺寸推断 8。

两点关于阈值的说明,避免被误读成"放水":

- **RGB565 的 maxErr 7 是紧界**。编码端是截断(`v>>3`)而非四舍五入,误差上界就是步长−1 = 7(G 通道 3),实测正好 7/3/7。位展开必须用高位补低位(`(v<<3)|(v>>2)`);若图省事写成单纯左移,白色只能到 248,maxErr 立刻破 7。
- **RAW 只在 y<390 判定**。参考图最下面 1/4 是 1px 宽的黑白 / 红蓝细纹,而 Bayer 每个位置只有一个通道的样本 —— 采样率不足,任何去马赛克算法都还原不出来,这是物理限制不是 bug。平坦区实测 maxErr 160~176 / PSNR 29.2~29.4,峰值全部落在彩条硬边界 0~1px 内(双线性跨阶跃必然过冲),边界之外逐像素精确。

**跨格式一致性**是最强的正确性证据:同一画面编成 YUYV/YVYU/UYVY/VYUY 四种排列、planar 与 semi-planar、YUYV 与 NV16,解出来必须**逐位相同** —— 排列偏移或色度上采样写错一处就会立刻暴露。

## mi_ebadge/cheer-preview.html — 自制应援效果(小程序预览的 web 移植)

把电子应援牌「自制应援」的编辑页预览从微信小程序搬到浏览器,用来**直接看效果**、对参数。设备端只收到枚举,所有动画都是预览端算的 —— 所以这份移植要还原的是那套**定时与运动约定**,而不只是观感:

- 预览固定 **24fps**,由 `setTimeout` 自累加**帧计数**驱动(不是 `requestAnimationFrame`,也不读墙上时间)。掉帧时动画**变慢而非跳步**,这点必须保留,否则同一段参数在设备上和预览里走过的位移量不一致。
- 所有运动量按 **466×466** 画布定义,再乘 `预览像素 / 466`。
- 背景相位 `phase` 的 1 个单位 = **1.5 秒**,每帧 `+1/36`;`speed` 只缩放背景,不影响文字。
- 文字画在背景**之后**,不参与背景的缩放、遮罩、模糊、旋转;彩虹只改文字颜色,不使用 `textColor`。

### 效果

| textFx | | bgFx | 周期 |
|---|---|---|---|
| `static` 静止 | 整块垂直居中 | `none` 静止 | 不动 |
| `scroll` 走马灯 | 右→左,单行 画布宽/4 每秒;多行第 i 行倍率 `1+i×0.4` | `breathe` 呼吸 | 2 秒 |
| `multiline` 滚动 | 整块自下而上,215 px/s | `pulse` 爆闪 | 0.4 秒 |
| `blink` 闪烁 | 1 秒一周期,余弦 | `open` 开幕 | 2.5 秒 |
| `rainbow` 彩虹 | 同速横滚 295 px/s;色相每秒 +36°,10 秒一圈 | `blur` 模糊 | 1.5 秒 |
| | | `rotate` 旋转 | 2 秒 |

发出前的别名改写 `step→open`、`shrink→blur`、`zoom→rotate` 也一并实现;未知枚举按「static / 静止全亮」回退。

### 功能

- 5 种 textFx × 6 种 bgFx 任意组合,分段按钮一眼看全所有枚举(面板直接由引擎导出的枚举表生成,不手写第二份)
- **圆屏** `466²`(文档基准)/ `360²` 两档,机身与画布都是圆的;另可切「方屏」做对照。360 上是同一套动画按 `size/466` 等比缩小
- **单行 / 多行**一键切换:单行把各行并成一行(空格分隔),多行按 `\n` 拆、去空行、**最多 6 行**
- 字号、字色、底色;**默认自带背景图**(内联 base64),也可**选图 / 拖图**(按短边居中裁正方),或清除回纯底色
- **dpr 1×/2×/3×** 切换 —— 用来验证「466 基准量 × size/466」在各尺寸下等比
- 逐帧可控:<kbd>空格</kbd> 暂停 / 恢复、<kbd>→</kbd> 单步、<kbd>R</kbd> 归零;画布下方实时给出 `frame / 秒数 / scrollOffset / phase / ink / 尺寸 / 行数`,方便对着数值核对
- **文字溢出告警**:超宽时报出裁掉多少(折算回 466 基准)。圆屏的可用宽度是该行基线处的**弦长**而非直径 —— 行离中心越远越窄,所以多行的首尾行比中间行更容易被切,这点纯看画面不容易察觉

圆屏裁切只是最外层一道遮罩,**不参与运动数学** —— 位移、相位、循环间距仍按方形画布算(文档的运动量都按 466 方形定义),圆只决定最后哪些像素留下来。

### 默认图

`preset-image.js` 是 `color_trans/img/badge-preset-image-9.png`(360×360 同心圆盾牌)的 base64 内联。选它的理由:本身是圆形,配圆屏不留死角;同心环结构能把 `bgFx rotate` 的「四环各自旋转」直接显示出来 —— **纯色底下 `rotate` / `blur` / `open` 的缩放和模糊是看不见的**(对均匀填充它们是恒等变换),所以默认带图比默认纯色更有用。

按项目惯例内联而不是走 `../color_trans/img/` 相对路径:`mi_ebadge/` 自包含,`file://` 下不会因跨目录加载失败而空屏。

### 使用

直接双击 `mi_ebadge/cheer-preview.html` 打开即可,无需服务器(离线可用)。

### 自测

动画逻辑全在 `cheer-preview.js`(UMD,不碰 DOM),所以能在 Node 里跑回归 —— 用 stub 的 2D context 记录每次绘制调用,把文档里给出的数值当 ground truth 核对:

```bash
cd mi_ebadge
node selftest.js     # 121 项:速度 / 周期 / 相位 / 行距 / 色相 / 枚举回退 / 缩放不变性 / 圆屏 / 排版 / 溢出
node pagecheck.js    # 47 项:内联脚本语法、id 对账、引擎 API 与面板枚举一致、默认图完整性
```

实测 **121/121 + 47/47 全绿**。几处值得一提的断言:

- **彩虹色相是闭环的**:0s `#ff0000` → 2.5s `#80ff00` → 5s `#00ffff` → 10s 回 `#ff0000`。文档里 `hue/30` 那段是 HSL→RGB 的扇区计算,与帧率无关,错写成按帧递增就会在换画布尺寸时偏色。
- **缩放不变性**用「滚过的画布占比」而不是绝对像素来判:1 秒滚过 `295/466 = 63.3%`,在 466@1× / 932@2× / 700@1× / 360@1× 各组合下**逐位相同**。`scrollOffset` 以 CSS px 累加、绘制时才乘 dpr,顺序写反了这条立刻挂。
- **「文字不参与背景变换」是真断言**:stub 的 `save`/`restore` 会真的存取状态,所以 breathe 半亮帧里文字仍是 `alpha=1`、blur 期间 `ctx.filter` 已复位。早先版本的 stub 只打日志不存状态,这条会测成假阳性。
- **「圆屏是纯遮罩」也是真断言**:同参数跑 30 帧,圆屏与方屏的 `scrollOffset` / `phase` / 文字坐标必须**逐位相同**。顺带钉住裁切的位置 —— `save → clearRect → arc(内切圆) → clip` 要早于背景和文字;`rotate` 自己也用 `arc`+`clip`,所以圆屏叠上去应是 `1 + 4 = 5` 次 `arc`,第一次半径为 `size/2`。
- **溢出按弦长判**:字号 100、3 行时首行 y = 233−135,弦长 `2√(233²−135²) ≈ 379.8` 而非 466 —— 同一段内容圆屏报溢出、方屏不报。溢出量折算回 466 基准后与画布尺寸无关(466 与 360 上都是 `+154px`,真实字体度量下核对过)。
- 走马灯 / 滚动 / 彩虹**不报溢出**(本来就跑出画布),但 `blink` 要报(位置与 `static` 相同)。
- `pagecheck.js` 还会把 `bindRange('x','xVal',…)` 这类**以字符串参数传入的 id** 一并对账 —— 这种拼错不会被 `$('x')` 的正则扫到,只能在运行时炸;默认图则会**把 base64 解回来验 PNG 签名与 IHDR 宽高**,并核对文件头声明的 `size` 与实际一致,免得注释骗人。

`blur` / `open` / `rotate` 的几何另外用棋盘图在 headless Chrome 下逐帧核过:`blur` 首帧 150% + 模糊 10 并在 0.5s 收清、1.5s 重新起糊;`open` 首帧 `shift=0` 幕布全闭、2s 后全开。

需要留意的两点:

- **纯色底下 `blur` / `open` / `rotate` 看不出差别**(缩放和模糊对均匀填充是恒等变换),所以默认带了图;对参数时别用纯色。
- **默认字号 96 在单行下必然溢出**(「一起 为你 发光」实测宽 ~620px vs 画布 466,超 154px),要到 **72** 才放得下。这里不做自动缩放 —— 原实现对超宽文字就是「居中画、超出即裁」,自动缩放会偏离设备行为,所以只把裁掉多少报出来。

## mi_ebadge/rotate/ — `bgFx rotate` 同向环扣贴图裁切

`bgFx = rotate` 把画面切成四个同心圆各自旋转,半径 `0.5 / 0.375 / 0.25 / 0.125`,角度交替:

| 环 | 466 直径 | 半径 / 边长 | 角度 |
|---|---|---|---|
| 外 | 466 | 0.5 | -90° → 0° |
| 2 | 349.5 | 0.375 | 90° → 0° |
| 3 | 233 | 0.25 | -90° → 0° |
| 内 | 116.5 | 0.125 | 90° → 0° |

相邻两环**反向**,所以能并成一张贴图「一起转」的只有转向相同的那些:**内圆 + 2 环**(都是 `90°→0°`),另一组是外环 + 3 环。这个工具把导入图片里的**内圆与 2 环**抠出来合成一张 PNG,尺寸 = 2 环外接正方形 = **`0.75 × 短边`**。

### 功能

- 拖图 / 选图进窗口,当场出图:输出图(棋盘格透明底)、取景对照图(虚线圈标出被抠走的那块)、**按真实角度旋转的实时预览**、以及「外环 + 3 环」另一组 —— 两组的亮区互补,一眼能看出切分干不干净
- 输出 **1× / 2× / 3×**,或保持透明、或垫一层底色;一键导出 PNG(<kbd>Ctrl</kbd>+<kbd>S</kbd>)或写进剪贴板
- 所有几何数字都由 `rotate-crop.js` 的 `RING` / `SPRITE` 推出来,面板里不留第二份常量

### 为什么边长是 0.75 且不留边距

圆绕**固定圆心**旋转,任何时候都内切同一个正方形,所以 2 环那组的贴图边长正好取它自己的外接正方形 `0.75 × 短边`。留边距(比如补到 1× 整图)会让贴图和 466 基准的比例对不上 —— 1/6、1/3…1/2 这些归一化半径就全错了。

导出是**透明 PNG**:3 环位置全透明,设备按黑底铺时不会漏出另一组的画面,两组叠加就是原图。

### 使用

直接双击 `mi_ebadge/rotate/rotate-crop.html`,无需服务器(离线可用)。

### 自测

```bash
cd mi_ebadge/rotate
node selftest.js     # 44 项:取景 / 环带归属(24 角度 × 4 尺寸)/ 抗锯齿 / 角度曲线 / 假 canvas 全管线
node pagecheck.js    # 38 项:内联脚本语法、id 对账、外部资源、常量与文档一致、面板不硬编码
```

实测 **44/44 + 38/38 全绿**。几处值得一提的:

- **取景与预览一致**:先按短边居中裁成正方形,再取以圆心为中心的 `0.75` —— 和 `cheer-preview.js` 的 `drawImageCover` 同一套。少这一步,贴图就和设备上看到的画面错位。
- **`drawImage` 的取景矩形是断言出来的**:`selftest.js` 用假 canvas 跑同一条 `renderSprite` 管线,直接核对 `sx/sy/sw/sh`(`1080×720` → `sx=270 sy=90 sw=540`),不是「浏览器里看着对」。
- **遮罩不依赖角度**:圆转多少度都内切同一正方形,所以环带只由半径决定。自测按 24 个角度 × 4 种尺寸采样,内圆与 2 环必须恒 `1`、3 环与外圈必须恒 `0`。
- **抗锯齿逐像素 4×4 子采样**,且只在边界 1px 内出过渡像素(270px 下约 2.1% 的像素是半透明,全部贴着边界)。
- 另外用 headless Chrome 逐帧核过:非对称标记旋转 `+45°` 后**各转 45°、半径不变**(实测 `0.4151 → 0.4144`),四色环图证明输出里只留下内圆与 2 环、角落全透明。

## progressiveJpeg/ — Progressive JPEG 首扫 vs 高斯模糊 对比

把 PNG 转成 **progressive JPEG**,解出它**第一段扫描**(只有 DC 系数)的画面,和原图做**高斯模糊**的结果并排比较 —— 用来回答「渐进加载时那张先出来的糊图,和直接上高斯模糊占位图,差在哪」。

结论(466×466 样图,q85 4:2:0):首扫只用 **4.2 KB / 7.7%** 的字节就给出 **19.77 dB / SSIM 0.567**;要让高斯模糊糊到同样的失真量,需要 **σ≈4.3**,而那需要整张图 **413 KB** 全部下载完。首扫的糊是**逐块保真**的(每 8×8 一个平均色,亮度轮廓、明暗、色彩分布都在位),高斯模糊则是**无差别抹平**,亮部会往暗部渗。

### 功能

- `make_progressive.py`:编码 progressive JPEG,解析 `SOF2` / 每段 `SOS` 的 `Ss/Se/Ah/Al`,按扫描边界**截断 + 补 EOI** 得到 10 张「只收到前 N 段」的合法 JPEG 并逐个解码
- 首扫给两个版本:**带 DC 平滑**(libjpeg / 浏览器真实所见)与**无平滑**(ffmpeg,能看到 DC 系数原本的 8×8 色块)
- 用 PSNR / SSIM 反解**等效高斯 σ**:最像首扫的 σ(像素 / 结构两种口径)、与首扫失真等量的 σ,并给出理论参考(盒式滤波 σ=w/√12)
- `progressive-jpeg-compare.html`:交互查看器,拖扫描段 / 拖 σ、并排或**分屏拖动**对比、差异热力图、按住 <kbd>空格</kbd> 看原图、一键导出三联对比 PNG
- 查看器里的 PSNR / SSIM 由 JS 独立算一遍(SSIM 用标准 11×11 高斯窗 σ=1.5),与 Python 的 `metrics.json` **逐位对得上**,互为验证

### 使用

```bash
cd progressiveJpeg
python make_progressive.py            # 需要 pillow / numpy / scipy / scikit-image;ffmpeg 可选
```

产物在 `out/`:`comparison.png`(六格总览)、`scan_stages.png`(10 段渐进过程)、`blur_stages.png`(σ 阶梯)、`metrics.json`、以及查看器用的 `data.js`。

跑完直接双击 `progressive-jpeg-compare.html`(图片已 base64 内联进 `data.js`,`file://` 下也能读 canvas 像素,无需起服务器)。换图:`python make_progressive.py --src 你的图.png -q 90`。

## progressiveJpeg/ — 双表法毛玻璃(嵌入式大 σ 近似)

`make_frostglass.py`。常规做法是拿大核卷积换 σ,这里反过来:**让 σ 从采样几何里免费长出来**。

```
JPEG scale=1/8 解码 = 每 8×8 块只取 DC = 宽 8 的 box    方差 (8²−1)/12 = 5.25
双线性上采样 8×     = 半宽 8 的三角核                  方差 8²/6     = 10.67
两者独立,方差相加  ->  σ_base = √15.92 = 3.99         一次卷积都没做
```

再在 59×59 的小图上叠 n 趟 w×w 的 box(小图 1 px 折算原图 8 px,方差按 64 倍放大),σ 可以推到任意大:`σ_total = √(16 + (64/12)·n·(w²−1))`。

**「双表」**指编码和解码用两张不同的量化表 —— 编码用 `Q_enc`(AC=255,把 AC 系数全量化成 0),写进文件的 `Q_dec` 则是 AC=1。两份码流的熵数据**逐位相同**,只有 DQT 那 126 字节不同,改表不需要重新编码。

### 实测(466×466 样图,Q(0,0)=8/16,4:2:0)

码流 **6,171 B**(bpp 0.227),是普通 q75 的 **0.142×**;折算 640×480 约 **8.5 KB**。

| 管线 | 公式 σ | 实测 σ | vs 真高斯 PSNR | SSIM |
|---|---|---|---|---|
| 1/8 + 双线性(无后处理) | 4.00 | **5.5** | 24.70 dB | 0.845 |
| + box(3)×1 · 常规毛玻璃 | 7.66 | **8.9** | 29.90 dB | 0.966 |
| + box(3)×3 · iOS 风格 | 12.00 | **12.7** | 33.22 dB | 0.990 |
| + box(5)×3 · CSS blur(20px) | 20.00 | **20.8** | 37.27 dB | 0.995 |
| + box(7)×3 · 极重虚化 | 28.00 | **29.1** | 40.00 dB | 0.996 |

σ≥8.9 起与真高斯**肉眼无法分辨**(SSIM ≥0.966),而真高斯需要全部 636 KB 像素在手。公式只叠了小图上的 box、漏掉上采样 tent 的贡献,所以**系统性低估 0.6~1.5**;要精确对齐 CSS `blur(Npx)` 请查「实测 σ」列,别直接用公式。

### 三个容易踩的坑(`failure_modes.png` 里有图)

- **单表法**(把 AC=255 留在文件里):一旦被 1/1 全解码就是振铃,与双表版最大差 **190 灰阶**
- **不改表**(`Q_dec` = `Q_enc`):1/8 下仍残留 **52 灰阶**,分通道看 `Y=0 / Cb=30 / Cr=30` —— 4:2:0 时色度 `_DCT_scaled_size` 被抬到 2,走 `jpeg_idct_2x2` 会吃低频 AC。所以**「表整形在 1/8 路径下无效」只对亮度成立**,`Q_dec` AC=1 在 4:2:0 下不是保险而是必需项
- **Q(0,0) 两表不一致**:增益 r 使 `像素 → 128 + r·(像素−128)`,是**围绕 128 的对比度缩放**而非亮度偏移。r=2 饱和 30.1%,r=4 饱和 48.5%,双向削波不可逆

### 平移不变性(方案外的发现)

box 的采样格点钉死在 8 的倍数上,平移不会被吸收。内容相对网格平移 0~7 px、对齐后比残差:

| 档位 | 双表 最大 / 平均 | 真高斯 最大 / 平均 |
|---|---|---|
| 1/8 + 双线性 | **100.0** / 5.06 | 29.0 / 0.03 |
| + box(3)×3 | 29.0 / 0.90 | 24.0 / 0.13 |
| + box(7)×3 | 19.0 / 0.76 | 18.0 / 0.32 |

静态壁纸无所谓;**滚动 / 摄像头场景会看到「呼吸感」**,σ 越大越轻(box 叠得多就越接近平移不变)。

```bash
python make_frostglass.py --sigma 15      # 反解 (w,n) 命中目标 σ

```

产物在 `out_frost/`:`overview.png`(管线四步)、`frost_vs_gauss.png`(五档位左右对照真高斯)、`failure_modes.png`(四种踩坑)、`metrics.json`、以及查看器用的 `data.js`。

## AJPEG/ — PNG → JPEG(YUV 4:2:0) + 尾部 RLE alpha 的转换与压缩率对比

把一张带透明通道的 PNG 拆成两半:**RGB 编成 baseline JPEG**(4:2:0,质量可调),**alpha 按 8 bit/像素取出后做 RLE 压缩**,再把 alpha 块拼到 JPEG 的 `FF D9` 之后。文件后缀仍然是 `.jpg`,任何图片查看器都能打开(只会看到不带透明度的 RGB 部分)。

目的很直接:**量一下这个方案的压缩率**——尤其想看清楚 RLE 到底吃不吃 alpha 的形状。

### 为什么 alpha 值得单独拎出来

JPEG 本身没有 alpha。常见做法(如 `pngquant` / WebP)要么丢掉要么整段无损存 alpha,这里走的是「JPEG + 自定义 RLE alpha」的嵌入式路线,和 HoneyGUI `image-converter` 的 `imdc` 格式一脉相承。RLE 是逐行 `[len:1][byte:1]` 节点流,run 上限 255,与 `tools/image-converter/compress/rle.ts` 的 `compressLine` **逐字节一致**。

所以压缩率**完全取决于 alpha 在水平方向上的连续度**:

| 图 | alpha 形状 | raw | RLE | 压缩率 |
|---|---|---|---|---|
| `opaque.png` | 全不透明 | 212.07 KB | **1.82 KB** | 0.9% |
| `alpha_sticker.png` | 圆角矩形 + 挖孔,硬边 | 212.07 KB | **3.53 KB** | 1.7% |
| `alpha_sticker_inv.png` | 上一张的反相 | 212.07 KB | **3.53 KB** | 1.7% |
| `alpha_soft.png` | 径向 + 线性软渐变 | 212.07 KB | **148.51 KB** | **70.0%** |

`alpha_sticker_inv.png` 是 `alpha_sticker.png` 的 alpha 取反(前景/背景互换),用来看压缩率对 **alpha 极性**有多敏感。结论是**完全不敏感**:反相后 payload 大小、节点数、行偏移表全都一模一样。因为 RLE 只判断"相邻是否相同",而取反是 0↔255 一一映射,相邻关系不变。四张图实测:

| 图 | 原 payload / 节点 | 反相后 | 偏移表 |
|---|---|---|---|
| `alpha_sticker` | 3,618 B / 1,809 | 3,618 B / 1,809 | 相同 |
| `alpha_soft` | 152,076 B / 76,038 | 152,076 B / 76,038 | 相同 |
| `opaque` | 1,864 B / 932 | 1,864 B / 932 | 相同 |

也就是说,**决定 RLE 效果的是 alpha 的"块状程度",不是"哪一边占大面积"**。一张"透明区占 58%、四周实体"的图,和它的反相版本压出来一样大。

**软渐变几乎压不动**——这是 RLE 的固有短板,不是实现问题。同一张 `alpha_soft` 用 PNG 的无损预测过滤器只要 13.01 KB,是 RLE 的 **11.4 倍**。所以脚本默认 `--rle-mode best`:当 RLE 反而比裸数据大时自动退回 RAW 存储(码流里用 `algo` 字段标出来)。

### 实测(466×466 样图,三档质量)

| 图 | q | JPEG | alpha 块 | AJPEG | vs PNG | bpp | PSNR | SSIM |
|---|---|---|---|---|---|---|---|---|
| alpha_soft | 85 | 55.53 KB | 150.35 KB | 205.89 KB | 55.8% | 7.767 | 34.84 dB | 0.978 |
| alpha_sticker | 85 | 55.53 KB | 5.37 KB | 60.91 KB | **17.3%** | 2.298 | 34.84 dB | 0.978 |
| opaque | 85 | 55.53 KB | 3.66 KB | 59.20 KB | **16.8%** | 2.233 | 34.84 dB | 0.978 |

关键点:**alpha 的成本和质量无关**。滑质量只动 JPEG 那段,`alpha_soft` 无论 q70 还是 q95 都固定背着 150.35 KB —— 图里但凡有大面积软过渡透明,JPEG 那头省下来的字节会被 alpha 原样吃回去。全不透明图加 q85 只有 59.20 KB(PNG 的 16.8%),而同样内容一旦有了软 alpha,就变成 3.5 倍。

### 换成真实素材更说明问题

拿一张 512×512 的图标(`actions-address-book-new.png`,71.7 KB / RGBA)跑:

| q | JPEG | alpha 块 | AJPEG | vs PNG |
|---|---|---|---|---|
| 75 | 20.12 KB | 41.62 KB | 61.75 KB | 86.1% |
| 85 | 25.35 KB | 41.62 KB | 66.98 KB | 93.4% |
| 95 | 41.08 KB | 41.62 KB | **82.70 KB** | **115.3%** |

**q95 时整个文件比原 PNG 还大 15%。** 这张图的 RLE 把 alpha 压到 15.5%(39.60 KB),看着不差,可 PNG 那边用预测过滤器 + DEFLATE 只花 7.56 KB —— **5.2 倍差距**。抗锯齿边缘的 alpha 是逐像素微调的一圈渐变,RLE 在这上面几乎无能为力,而 PNG 的行内预测恰好就是为这种平滑曲面设计的。

所以对**带抗锯齿边缘的 UI 素材**,这个方案只在 JPEG 侧真的省字节时才划算;一旦质量要求高(q95),叠加的 alpha 会把收益全吃掉。它真正适用的场景是**alpha 大面积恒定**的图(纯色背景抠图、遮罩、图标在纯色上),那时 RLE 能压到 1~2%,和 JPEG 叠起来就是纯赚。

### 文件布局

```
[0 .. J)                baseline JPEG, YUV 4:2:0, 以 FF D9 结束
[J .. J+16)             alpha 块头
[J+16 .. J+16+4(h+1))   行偏移表, (h+1) × u32 LE, 相对 payload 起点
[...)                   payload:RLE 节点流(len:1 + byte:1)或裸 alpha
[末尾 12)               尾部索引:jpeg_size u32 | block_size u32 | 'AJP1'
```

alpha 块头 16 字节:`'AJP1'` magic | `u16 width` | `u16 height` | `u8 algo`(0=RLE / 1=RAW)| `u8 feature_1` | `u8 feature_2` | `u8 flags`(bit0 = 含透明像素)| `u32 payload_size`。行偏移表的形状照搬 `imdc_file_t`,尾部索引让解码端能**从文件末尾倒着定位**,不必猜 JPEG 在哪里结束。

### 功能

- `make_ajpeg.py`:PNG → AJPEG 转换,支持**单个文件或整个文件夹**(递归),`-q 70,85,95` 一次出多档质量
- alpha 自动择优:RLE / RAW 谁小用谁(`--rle-mode best|rle|raw` 可强制)
- 每张图**回环校验**:重新解析自己产出的 `.jpg`,解码 alpha 并与原图逐字节比对,不一致直接报错
- PSNR / SSIM(11 点高斯窗 σ=1.5),给出 vs PNG 的比例、bpp、体积构成
- `ajpeg-compare.html`:单文件交互查看器,支持**直接导入本地图片和整个文件夹**,**中英双语可切换**
- `ajpeg-decode.js`:RLE 编解码器,**页面和自检脚本共用同一份**(避免两份副本只有一份是对的)
- `verify_ajpeg.cjs`:加载上面那个编解码器,和 Python 的 adler32 对账,双向验证编码与解码

### 查看器:导入本地图片

### 两个踩过的坑

**`lineOffsets` 是压缩后 payload 里的字节位置,不是解压后的像素位置。** 第一版 JS 解码器拿 `offsets[height]` 当输出缓冲区大小,结果 `alpha_soft` 只解出 152076 / 217156 字节 —— 正好是 70% 的压缩率,看着特别像"解对了"。adler32 对账把它揪出来了。

**`data.js` 里的 payload 是 base64 字符串,必须先 `atob` 再喂给解码器。** 漏了这一步,`payload[p]` 取到的是字符码而不是字节,解出来一片 0 —— 页面上表现为 alpha 全透明、图看不见,校验显示 `50710001 ≠ cb3e2540`。当时自检脚本写的是 `b64(a.payload)` 所以是绿的,而页面里是裸的字符串,两份副本不一致。

所以现在解码器只有一份(`ajpeg-decode.js`),自检直接 `require` 它 —— 不再可能"测试过了但页面是坏的"。自检还会额外断言 alpha 不能全零,专门堵这个漏洞。

## 10_scale_img/ — 图片缩放算法对比(最近邻 vs 双线性)

导入一张图,把它缩到 **0.63 倍**(可调)后,并排 / 叠加分割看两种算法的**实际显示效果**。不是什么理论推演,就是「缩完到底长什么样」。

### 看什么

缩到 0.63 倍是个不好伺候的倍数:双线性的采样核宽度恒为 2 个源像素,而目标像素要覆盖 `1/0.63 ≈ 1.59` 个源像素 —— 核比覆盖范围窄,细线和纹理就会漏采样。两种算法的失效方式完全不同:

- **最近邻**:整块整块地丢行丢列,硬边(眼线、睫毛、文字)出现台阶和锯齿,但颜色本身是原样搬运的,不发灰
- **双线性**:锯齿没了,但细节被拉糊,细线会变淡甚至闪断

用 `wp-3.png`(466×466 → 294×294)实测:

| | PSNR vs 另一侧 | PSNR vs 面积平均(正确答案) | 耗时 |
|---|---|---|---|
| 最近邻 | 36.10 dB | **34.56 dB** | 0.8 ms |
| 双线性 | 36.10 dB | **45.21 dB** | 2.0 ms |

两者彼此差 36 dB 看着「差不多」,但拿面积平均当参照,双线性比最近邻准了 **10.6 dB**。最大单通道差 115/255。

所以工具里放了个**面积平均(Area/box)作为参照物**,它不算对比项 —— 它才是缩到这个倍数时「正确」的样子。差异图默认就以它为基准,一眼看出谁在犯错。

### 功能

- **导入**:拖进来 / `Ctrl+V` 粘贴 / 点按钮选文件;内置 `wp-3.png` 一键载入
- **倍数可调**:滑块 + 数字框 + 0.63/0.5/0.75/0.9/0.33/0.25 快捷档,0.05–4 倍
- **算法任选**:左右各一个下拉(最近邻 / 双线性 / 面积平均),两边自动互斥,可一键交换
- **两种对比视图**:并排(各占一半)、叠加分割(中间一条可拖的分界线,同一块区域左右对照)
- **像素级检视**:滚轮以光标为中心缩放、拖动平移、1×–8× 快捷档,放大时**关掉 canvas 平滑**,看到的是真像素而不是又插值一次的糊图
- **放大镜**:跟光标走的 12×12 输出像素特写,左右并排,底下实时显示两侧的 RGB 和对应的源图坐标
- **差异图**:按通道最大差 × 增益(1–40)出灰度图,基准可选「面积平均」或「另一侧算法」
- **按住空格**临时看原图(缩放平移不变,只换内容)
- **指标**:PSNR / 耗时,自动计时取 3 次最小值

### 使用

直接双击 `scale-compare.html`。示例图已由 `make_sample.py` base64 内联进 `sample-data.js`,所以 `file://` 下打开就能用 —— 不用起服务器,也绕开 `drawImage` 外部文件污染 canvas、`getImageData` 抛 `SecurityError` 的问题。

```bash
python make_sample.py                 # 重新生成 sample-data.js(默认打包 wp-3.png)
python make_sample.py 别的图.png       # 换一张内联
node verify_scale.cjs                 # 算法内核自检(不需要浏览器)
node smoke.js                         # 无头 Chrome 端到端冒烟(--headful 可看过程)
```

### 实现

`scale-core.js` 是纯函数内核,浏览器(`window.ScaleCore`)和 Node(`require`)共用一份 —— 这样自检测的就是页面上跑的代码,不会出现「测过了但页面是坏的」。

三个算法都用**像素中心对齐**的约定:`目标(x,y)` 的中心映射到源图的 `(x+0.5)·sw/dw - 0.5`。这是 GPU 和大多数库的默认约定,也是 `0.63` 这个倍数下最贴近实际渲染的假设。

`verify_scale.cjs` 里带了断言(而不是只看输出顺眼):最近邻的输出值必须**全部是源图的原始像素值**、双线性放大时必须产生新的中间色、1:1 时三种算法逐字节还原、纯色图缩放后不变色、透明边缘不出黑边(alpha 预乘插值)、缩到 1×1 不越界。第 8 项直接拿 `wp-3.png` 跑一遍并断言「双线性比最近邻更接近面积平均」。

`smoke.js` 用 DevTools 协议驱动无头 Chrome(不依赖 puppeteer):载入 → 改倍数 → 切视图 → 开差异图 → 换算法 → 缩放 → 放大镜,逐项断言并把 `console` 的 **error** 当失败(warning 只打印)。最后截一张图。

## 11_polaroid/ — 宝丽来 i-Type 显影盒 3D 预览(WebGPU)

一个立起来的「板砖」造型显影盒 —— 白壳、银边、彩色条纹，后背连着顶盖像磁带机舱门一样向后斜开，露出内腔和插在里面的一沓相纸。**只做开门动画，不做显影过程。**

### 造型依据

外观主参照宝丽来官方 i-Type 包装盒（`ref/NOTES.md` 有实测数据）：

- **正面**：冷白底（`#F0F0EC`） + 左侧三条竖色带（红 `#D65649` / 橙 `#EF8C49` / 黄 `#FFC857`，占宽 32%），白色大字 `Color i-Type Film` 压在色带上，底部黑色 `polaroid` 字标
- **书脊**（左右侧面）：五色块堆叠（蓝绿黄橙红），下方留白竖排 `polaroid`
- **挂耳**：顶面左右两侧棱上的**水平插销**，沿棱方向（Z 轴）伸出一截悬空销子，两端有支架连回壳体，背带从销子与壳体之间的空隙穿过
- **红钮**：顶面朝上，落在左侧那道**加宽的门边**上（左 1.50cm vs 右 0.50cm）—— 这是电子产品，不是相机快门

### 舱门机构

顶面的门四周都留边，不顶到正面：

```
        ┌──── 门缝(前 0.42cm)────┐
   ┌────┴────────────────────┬──┐
   │  左边框 1.50cm(红钮)     │右│ 0.50cm(挂耳)
   │  ┌────────────────────┐ │  │
   │  │      舱门顶唇       │ │  │
   │  └────────────────────┘ │  │
   └─────────────────────────┴──┘
              ↓ 绕底后棱旋转 52°
```

铰链在 `(0, 0.3, -1.2)`，绕 X 轴负向旋转，门顶向后上方掀起。门板覆盖上半段后背（5.6cm），下方 6.2cm 是固定后背。

### 实现

- **three.js r187 WebGPU 构建**已 vendored 到 `lib/`（`three.core.js` / `three.tsl.js` / `three.webgpu.js`），走 importmap 加载，不依赖 CDN
- 优先用 **WebGPU** 后端；浏览器不支持时 three 会自动回退 WebGL2，页面照常工作
- 环境贴图是**程序化生成的 equirect 画布**（上亮下暗 + 几个柔光箱），经 PMREM 预卷积，不依赖外部 HDR 文件
- 所有印刷（正面色带/文字、书脊色块、顶面细色带、相纸画面）都是 **canvas 2D 程序化绘制**，零外部图片
- 壳体用 `Shape + ExtrudeGeometry` 做圆角砖块，壁厚 0.18cm，开门后能看见真实内腔
- 色调映射用 **AgX**，主光 3.4 / 环境 0.62，避免大面积白色过曝

### 使用

```bash
# 需要一个静态服务器(importmap + ES module 不能用 file://)
python -m http.server 8000
# 然后打开 http://localhost:8000/11_polaroid/
```

拖拽旋转 · 滚轮缩放 · 双击复位 · 底部按钮或滑块控制舱门。

### 冒烟测试

```bash
node smoke.js        # 无头 Chrome 驱动,跑完自动清理进程
```

用 DevTools 协议驱动（不依赖 puppeteer），检查 WebGPU 可用性、页面就绪、网格数量、控制台错误，并从 4 个机位截图到 `_shots/`。

**进程清理**是这块的重点：Chrome 在 Windows 上会 fork 出新进程后让启动器退出，所以 `spawn` 拿到的 PID 往往已经死了。脚本改用 **profile 目录路径**定位所有相关进程，用 `taskkill /T /F` 杀整棵树，并覆盖 `SIGINT / SIGTERM / SIGHUP / uncaughtException` 全部退出路径，外加 120s 硬超时兜底。实测连续多次运行，残留进程始终为 0。

### 参数

全部尺寸、配色在 `src/core.js` 的 `DIM` / `COL` 里，改一个数字即可。真实 i-Type 相纸是 107.5 × 88.5mm（画面 79 × 79mm），盒体按相纸尺寸外扩而来。
