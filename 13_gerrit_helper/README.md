# Gerrit Helper

贴在屏幕边缘的 Gerrit 任务跟踪器。竖排圆环一屏看完全部在途 change，悬停出卡片看时间线，
状态变化弹系统通知。Electron 桌面应用，不是网页。

## 跑起来

```bash
npm install          # 首次会下 Electron 二进制（~230MB）
npm start            # 正常启动，没配服务器时会先弹设置窗
npm run demo         # 演示模式：假数据，不连服务器
npm test             # 纯逻辑单测（node:test，不用起 Electron）
npm run build:backdrop  # 编译亚克力 helper（Windows 11，只需一次）
```

配置和日志在 `data/`（开发时）或 exe 同级 `data/`（打包后）。

## 界面

```
                                          ┌─┐
                                   屏幕右边缘 ⬤  ← 竖条：每条 change 一格
                                          ⬤     环 = Code-Review 进度
  ┌──────────────────────────────┐        ⬤     颜色 = 状态
  │ base   发起人 林工 [进行中]│◄── 悬停  ⬤
  │ Fix Wi-Fi handover stall     │
  │ PS 4  CR +2  CI —  刚刚      │
  │ ● 林工 Code-Review+2 这版… │  ← 时间线最多 184px 高，超出自己滚
  │ ● ci-bot CI passed           │
  │ [在 Gerrit 打开] [刷新]      │
  └──────────────────────────────┘
```

- **发起人**：卡片标题栏写这条 change 的 owner（`发起人 林工`），
  时间线每一行再带上那条评论/打分的作者 —— 谁开的、谁传的、谁打的分都在
- **卡片背景比竖条厚一档**：竖条只有圆环和数字，卡片是成段文字，
  同样的透明度在花哨背景上根本读不清（`--glass-alpha` 按 surface 分别取值）
- **环的颜色**：绿=CR+2 可提交、橙=待我评审、红=CI 失败、蓝=已提交、灰=已放弃
- **环里的字**：`+2` / `+1` / `CI` / `✓` / `✕`
- **排序**：默认「紧急度」CI 失败 → 待我评审 → 待提交 → 我提交的 → 其他 → 已放弃；
  设置里可切「最近更新优先」
- **一屏放不下**：竖条最多显示十来格，滚轮翻页；总数在托盘提示里
- **卡片的收放只认一条规则**：指针不在「竖条 ∪ 卡片 ∪ 走廊」里超过 260ms 就收。
  不依赖 `focused` 这类间接状态 —— 间接判断只要有一处没跟上，卡片就永久留在屏幕上
- **状态变化主动弹气泡**：每次刷新后，状态有变的格子会自动弹出卡片（停留 6 秒），
  顶部有一条高亮说明写清楚变了什么（`#10188 Code-Review 2 → +1`），
  CI 翻红/恢复、构建开始/成功/失败/等待确认都在内。用户这时去碰悬浮层，
  主动气泡立刻让位给正常悬停，不会抢操作。和通知共用同一套开关。
- **「刷新」按钮会把过程演出来**：点下去按钮变成「刷新中」并转圈（禁用，防连点），
  主进程拉完一轮后推到「已更新」（失败是红字「刷新失败」），1.2 秒后回到「刷新」。
  状态由主进程推（`running → done`），渲染层只负责画 —— 卡片重画时也会按当前状态复原。
  失败和超时都有兜底：15 秒没结果就收掉动画，写一条日志。
- **卡片时间线按时间倒序**：最新的在最上面（构建卡里的 stage 明细也一样，按开始时间倒序）
- **卡片时间线**：最多带 40 条，超出 184px（约 6 行）的部分在卡片内滚动，
  操作按钮始终钉在卡片底部。不再显示「共 N 条」——条数看滚动条就知道，
  滚动条也去掉了两端的箭头按钮，滑块跟列表上下对齐
- **启动头几秒是一个转圈 + 「读取中」**，不是「还没有跟踪的 change」。
  第一轮拉取要 4–8 秒（SSH 往返 + Jenkins），这段时间面板本来就是空的 ——
  以前直接显示"没有跟踪项"，看起来像项目丢了，而且静态文字看不出来它在动
- **加载态的形状跟配置一致**：贴在边上就是带凹肩的形态，悬空就是四角圆角。
  为此加载块是**居中在玻璃体里**（`bodyInset = 两端留白`），长度按
  「加载块 + 两个肩位」算 —— 贴边 64×112、悬空 64×72。
  否则凹肩那一段是收窄的，环压在上面就会被切掉一截
- 模式：常驻显示 / 靠边自动隐藏（光标靠边 140ms 后滑出）
- **自动隐藏模式下，启动时先亮着，等第一轮数据到了再保持 2.5 秒才收起**：
  否则一启动就是"只剩个小把手"，不知道它停在哪、有没有起来。
  计时不按"启动了几秒"算 —— 本来就是想让人看见"有哪些格子"，数据没到的亮相没意义
  （拉取要 4–8 秒，固定计时会在数据到达前就收掉）。一直拉不到数据时 15 秒兜底。
  收起走的是正常动画（先 250ms 淡出竖条，淡完再让把手 160ms 淡入）；
  这期间鼠标已经压在竖条上的话，收起会自然推迟
- 悬停出卡片后，光标可以移到卡片上点按钮 —— 竖条和卡片之间的几像素空隙算"过渡带"，
  不会被误判成"鼠标离开了" 

## 两条通道：SSH（默认）和 HTTP REST

```
ssh -o BatchMode=yes -o ConnectTimeout=8 -p 29418 user@host     gerrit query --format=JSON --current-patch-set --comments "status:open owner:self limit:50" --
```

| | SSH | HTTP REST |
|---|---|---|
| 凭据 | 复用 `~/.ssh` 密钥，**不碰任何口令** | HTTP password 或 `~/.gitcookies` |
| SSO 墙 | 不受影响 | 可能被门户挡住 |
| 时间线 | `--comments`（只有当前 patch set 的评论） | `o=MESSAGES`（完整，含历史 patch set） |
| 身份 | 靠查询来源（`owner:self` / `reviewer:self`） | `/accounts/self`，被关掉时同样回落到来源判断 |

默认 `transport: auto` —— 本机有 `ssh` 就走 SSH，否则回落 REST。三条实现细节：

1. **能力探测只做一次。** `--current-patch-set` 在部分版本被弃用。启动时用 `limit:1` 的空查询试一遍，
   从 stderr 里认出哪个 flag 不被支持，之后一直用降级后的组合 —— 而不是每轮失败重试（那等于每轮多打一次 ssh 往返）
2. **末尾必须有 `--`**，否则查询里的减号会被 ssh 当成选项
3. **`BatchMode=yes`** 保证密钥不可用时立刻失败，不会卡在一个要口令的提示上

实测（Gerrit 3.12.2）：`--current-patch-set` 和 `--comments` 都还支持，能力探测不用降级；
两条查询各约 500ms，合成的竖条数据正确。

> **服务器地址要带网页入口的路径前缀。** Gerrit 的网页可能在子路径下
> （这台是 `https://cn4soc.rtkbf.com/gerrit`，根路径 `https://cn4soc.rtkbf.com` 是 nginx 默认页）。
> 少了 `/gerrit`，卡片上的链接全是 404 —— 而且因为走 SSH 通道，REST 那条路一直没被用到，
> 这个错就一直没暴露。项目名里的 `/` 也不能整体 `encodeURIComponent`（会变成 `%2F`，
> 链接同样打不开），现在是按路径段编码。

> **SSH 通道下卡片链接要换成 https。** `client.base` 是 `ssh://user@host:29418`，
> 拿它拼出来的 `url` 浏览器打不开，"在 Gerrit 打开"会静默失败（https 白名单挡掉）。
> 现在优先用配置里的 http(s) 地址，只有纯 SSH 配置时才由 `webBase()` 把
> `ssh://user@host:29418` 转成 `https://host` —— 网页入口和 SSH 是同一台机器，只是端口不同。

## 第一次启动：自动读本机配置

启动时如果还没有配置，会先扫一遍本机，识别到了就直接用，然后弹设置窗让你确认认证方式：

| 线索 | 拿到什么 |
|---|---|
| `~/.gitconfig` 的 `[url "ssh://host:29418"]` 重写 | 服务器 host + port（`insteadOf` / `pushInsteadOf` 都认）—— 全局唯一，最省事的一条 |
| 扫描目录 / 工作目录里的 `.gitreview` | 服务器 host + port + project（往下找 3 层，跳过 `node_modules` 等） |
| `git remote -v` 的 URL | `ssh://user@host:29418/...` 或 `https://host/...` |
| `~/.ssh/config` 的 Host 块 | HostName + User（认 Port 29418 或名字含 gerrit 的） |
| `git config --global` | `gitreview.username`，否则用 `user.email` 前缀当用户名 |

识别到服务器之后，跟踪项**默认自动就是这两条**，不用再一行行填 change 号：

```
q:owner:self status:open        ← 我提交的、还开着的
q:reviewer:self is:open         ← 等我评审的
```

**凭据一律不自动读。** 密码和会话 cookie 不探测、不复制、不落盘：

- 有 HTTP password → 选「HTTP password」填进去，用系统 DPAPI 加密保存
- 走 SSO 门户、没有 HTTP password → 选「复用 ~/.gitcookies 的 SSO 会话」，
  客户端**每次请求现读** `~/.gitcookies`，不复制进配置

设置窗里有一个「重新检测本机配置」按钮，改了扫描目录可以随时重扫。

## 配置

设置窗（托盘图标）里填：

| 项 | 说明 |
|---|---|
| Gerrit 地址 | `https://gerrit.example.com`（带子路径如 `/gerrit` 也认） |
| 用户名 + HTTP password | 密码在 Gerrit 的 **Settings → HTTP Credentials** 生成，不是登录密码 |
| 传输方式 | 自动 / 仅 SSH / 仅 HTTP REST |
| SSH 端口 · 用户 · 私钥 | 用户留空则用上面的用户名；私钥留空则用 `~/.ssh` 默认密钥 |
| 认证方式 | HTTP password / 复用 ~/.gitcookies / 匿名（**仅 REST 通道用得上**） |
| 跟踪项 | 一行一个，见下 |
| 排序 | 紧急度优先 / 最近更新优先 |
| 只看最近 N 天 | 默认 **14 天**；滑杆 0–60，也可以直接输入天数（0 = 不限） |
| 背景不透明度 | 0–100，控制**悬浮层**（竖条 + 卡片，同一个值） |
| 设置窗自身不透明度 | 0–100，**独立设置**，默认 92% —— 调参数时希望设置窗实一点、悬浮层透一点 |
| 吸附到屏幕边缘 | 默认开。开 = 松手时靠近边缘才吸住（左/右/上/下，贴上边或下边会横排）；关 = 完全自由，但仍在工作区内 |
| 扫描目录 | 自动检测 `.gitreview` 的起点（高级里） |

跟踪项写法：

```
10231                                  ← change 号
I1a2b3c4d...                           ← Change-Id
https://gerrit.example.com/c/proj/+/123 ← 直接粘链接
q:reviewer:self is:open                ← 待我评审
q:owner:self status:open               ← 我提交的
q:project:platform/frameworks status:open
```

## Jenkins 构建监控

和 Gerrit change 混排在同一根竖条里：环 = 整体进度，中间字 = 当前 stage 首字母，
颜色 = 在跑(蓝) / 成功(绿) / 失败(红) / **卡在等人工确认(橙)**。

卡片里有一排**横向节点**，所有 stage 摆成一行：走完的实心、当前那步放大发光、
没到的只有暗点，连线跟着走完的段填色。下面一行写「第 3/7 步 · 当前 stage 名」，
再下面是每个 stage 的明细（名字 + 耗时）—— 一眼看进度，需要细节再往下看。

**"还没轮到"的节点是补出来的。** wfapi 只返回已经进过的 stage，后面的根本不在数组里 ——
不补的话卡片上只有"走了几步"，看起来像一共就这么几步。

参照名单从**最近一次跑完的构建**里取，而且要在两次之间挑最完整的：
实测某个 job `lastCompletedBuild` 只有 2 步（那次中途被中止），`lastSuccessfulBuild` 有 11 步 ——
只认前者就会一个都补不出来。所以两个都试、取 stage 多的那份，缓存 10 分钟
（空结果只缓存 1 分钟）；构建正常跑完时也顺手用它的完整名单更新一次。

补的时候按名字对齐：只补"当前最后一步之后"的部分，参照里前面有、本轮却没有的当作被跳过。
补出来的节点只出现在横向节点条上，不进下面的明细列表 —— 卡片不会被 11 行撑开。

配置：设置 → 构建 → Jenkins 地址 + 用户名 + API Token + 一行一个 job 路径。
Token 在 Jenkins 右上角 **用户名 → Configure → API Token** 生成。

**构建失败会自动下控制台日志**（设置 → 构建 →「构建失败后自动下载控制台日志」，默认开）：
状态迁到 `FAILURE` 时按卡片按钮那条路下一份，下完弹「构建日志已保存」通知。
只认 `FAILURE`（`UNSTABLE` / `ABORTED` 不下）；同一轮已经在下载时不会重复下。

数据来自两个接口：

| 接口 | 用途 |
|---|---|
| `/lastBuild/api/json` | `building` / `result` / `estimatedDuration` |
| `/lastBuild/wfapi/describe` | `stages[]`：每个 stage 的名字、状态、起止、耗时 |

### 每一段的耗时是怎么来的

三个来源，优先级从高到低，卡片上会用不同写法区分：

| 来源 | 卡片上的样子 | 说明 |
|---|---|---|
| `stages[].durationMillis` | `18m 58s` | controller 记的，正常都是正数，直接用 |
| `now − startTimeMillis` | `已跑 12m 30s` | 正在跑的那一段。`durationMillis` 在跑的时候恒为 0，只能自己算 |
| 内部步骤时间戳还原 | `≈ 4s` | 见下面 |

**负数怎么办。** `durationMillis` 偶尔会是负数 —— 实测遇到过 `−103948`：agent 的时钟比
controller 慢，`end − start` 跨了两个时钟。直接显示会变成负的时间，所以拿这一段内部
步骤（`stageFlowNodes`）的时间戳还原：那些是 controller 侧记的，
「最后一步的开始 + 耗时」减去这一段的开始，就是可信的实际耗时。每个 `(构建号, 节点)`
只多问一次，构建换号就清空。

三样都拿不到才显示 `—`（以前会显示成"时钟不同步"，那是原因不是数据）。

**两个必须处理的坑**（真机上实测到的）：

1. **构建中 `duration` 恒为 0** —— 进度只能用 `(now − startTimeMillis) / estimatedDuration`
2. **`stage.durationMillis` 可能是负数** —— controller 和 agent 时钟不同步，
   实测遇到 `-123267ms`。负值夹到 0 并在卡片里显示"时钟不同步"，不显示负数

还有一种状态是 `PAUSED_PENDING_INPUT`（流水线在等你点确认），比构建失败更该提醒。

### 下载某一次构建的控制台日志

Jenkins 给的是纯文本接口 `/job/<job>/<构建号>/consoleText`，和前面两个接口同一套认证
（Basic + API Token），所以不需要额外配置。

构建卡片底部三个按钮并排：**打开**（在 Jenkins 里打开这一轮）/ **下载日志** / **刷新**。
点「下载日志」后按钮变「下载中…」，下完变「已保存」并弹一条系统通知（点通知打开所在文件夹）。

命令行也能下，跑完退出，用来做自检或批量取日志：

```bash
electron . "--download-console=ReleaseBuild~HoneyComb~bb2Ultra~Acut/266"
```

日志落在**设置 → 构建 → 控制台日志下载目录**，留空就是程序目录下的 `build_log`
（第一次下载时自动创建，开发时就是项目里的 `13_gerrit_helper/build_log`）。
文件名 `job名-构建号-console.txt`，job 名里的 `~` 换成 `_`；同一轮重复下载会覆盖。
实测一次 570KB / 不到 1 秒。**入口只给 job 名和构建号**，地址永远来自配置里的 Jenkins 地址。

三个和状态接口不一样的坑：

| 坑 | 处理 |
|---|---|
| `lastBuild/consoleText` 会下错构建 | 地址必须带**具体构建号**（下载要几十秒，这中间可能起了新构建） |
| 几十 MB，整块 `.text()` 进内存 | 流式写盘，先写 `.part` 再改名 —— 半截文件不会看起来完整 |
| 总时长说不准，固定超时要么误杀要么卡死 | 按"多久没收到新数据"算（默认 30s 无数据才断） |

构建还在跑时也拿得到，返回到目前为止的全文 —— 末尾那行可能是半截。
同一轮构建反复下也没问题：名字里带构建号，不会和上一轮混在一起（只是会覆盖自己）。

## 设置窗

左侧导航 + 右侧单栏滚动，五个分栏：服务器与认证 / 跟踪项 / 显示 / 通知 / 高级。
窗口无边框、圆角和投影自绘，标题栏可拖动，和悬浮层用同一套色板与尺寸。

> 注意：透明窗口里 `rgba` 变量嵌套（`--glass: rgba(var(--rgb), var(--alpha))`）
> 作为 `background` 解析不稳定，所以设置窗的底色是由 JS 算好 rgba 后写进 `style` 的，
> 不依赖 CSS 变量。悬浮层的 `fill: var(--glass)` 没有这个问题。

### 会提醒哪些动态

| 事件 | 触发 |
|---|---|
| `status` | 提交 / 放弃 |
| `cr` | Code-Review 最高分变化 |
| `review` | **有新的 reviewer 参与投票**（最高分没变也算 —— 两个人各给 +1，max 一直是 1） |
| `comment` | **有新评论**（带作者和 60 字摘要） |
| `patchset` | 上传新 patch set |
| `ci` | CI 从通过翻失败 / 从失败恢复 |

`review` 和 `comment` 靠 SSH 的 `--comments` 拿数据；REST 通道需 `o=MESSAGES`。
一次刷新超过 3 条会合并成一条通知；跨轮用事件 id 去重，重启后清空。

## 构建结束发微信（接 14_wechat）

Jenkins 那边"跑完了 / 卡住了"→ 发一条微信。设置 → 通知 → **构建结束发微信** 打开即可，
流程用 `14_wechat` 里录的那份（默认同级目录的 `14_wechat/build/recorded.json`）。
下面的**发一条测试消息**会立刻回放一次（不用等构建，也不用先保存表单），用来确认流程和坐标。

**代码是搬过来的，不是子进程调过去的。** `src/wechat/` 下的 `player.js / steps.js / ps.js / win.ps1`
和 `14_wechat/src/` 里同名文件**逐字节相同**（`tests/wechat.test.js` 有一条检查，13 单独拷出去用、
找不到 14 时自动跳过）。要改回放逻辑请改 14 那边再拷过来 —— 这边只多了一个 `index.js` 薄壳。
好处是 13 保持"拷走整个文件夹就能跑"，不依赖 14 的目录位置、也不依赖 PATH 里的 node。

**正文塞进哪一步：流程里最后一处粘贴。** 14 的流程是「点搜索栏 → 粘贴关键词 → 点结果 →
粘贴正文 → 回车」，最后那次粘贴就是消息正文，前面那些导航粘贴原样保留。流程里没有粘贴
就直接报错，不会把空消息发出去。

**只发这五种状态**：`SUCCESS / FAILURE / UNSTABLE / ABORTED / PAUSED_PENDING_INPUT`。
`IN_PROGRESS` 不发 —— 否则每分钟一轮轮询都会命中一次状态迁移。文案长这样：

```
【构建失败】bb2Ultra~Acut #266
ReleaseBuild~HoneyComb~bb2Ultra~Acut
出事的步骤：Keil Build
https://cn4soc-jks.rtkbf.com/job/ReleaseBuild~HoneyComb~bb2Ultra~Acut/266/
```

**一次只发一条。** 回放会把微信拽到前台再模拟点击，两条并行会互相点飞，所以走队列
（最多堆 3 条）；同一个 `(job, 构建号, 状态)` 只发一次，写失败会弹一条桌面通知。

**自动触发比手点更容易失败，所以要重试。** Windows 有前台锁：只有"用户正在操作的进程"
才抢得到前台。手点「发一条测试消息」时我们正是那个进程，稳；定时器触发时不是，
`focus` 失败 → 整条发送中止。实测两次自动发送都卡在
`微信窗口没能前置（被别的窗口抢走，或客户端被锁）` 这一句上。
现在失败会自动重试 **3 次（8s / 16s）**，用户这时候往往正好切回微信；仍然失败才弹通知。

代价和 14 一样：发送期间抢焦点 1~2 秒，微信不在前台、或坐标上盖着别的窗口都会中止 —
日志里 `[wechat]` 开头那几行能看出是被哪道闸拦住的、第几次尝试。

> 注意：`win.ps1` 必须是 **UTF-8 with BOM**，拷贝时别转编码，否则 Windows PowerShell 5.1
> 会按 GBK 解析中文注释直接报语法错。

> 另外：`ps.js` 是按 `__dirname` 找 `win.ps1` 的。将来打包成 exe 时这两个 `.ps1` 不能留在
> asar 里（powershell 读不了 asar 内的路径），要 `asarUnpack` 或 `extraResources`。

## 关键实现

**窗口是真·非矩形。** 轮廓用一份 `M/L/C` 命令列表描述，三处消费：渲染层画成 SVG 填充、
`setPolygons` 光栅化成 Windows region 交给 `win.setShape()`、卡片尾巴和凹肩都靠它。

**鼠标不吃 DOM 事件。** 窗口透明且穿透时收不到任何事件，所以命中测试全在主进程用
`screen.getCursorScreenPoint()` 轮询（露出时 40ms，静默时 90ms）。

**不用的时候是真隐藏。** 早期版本"隐藏"只是把窗口透明度调到 0，窗口本身仍是
`WS_VISIBLE` 状态 —— 只要有任何一处把透明度写回去（淡出被打断、窗口重建、DWM 刷新），
那块面板就永久糊在桌面上。现在不显示时直接 `hide()`，渲染层面就不存在，任何状态错乱
都不可能让它重新出现。

**淡入 + 瞬隐。** 显示可以渐变，隐藏必须立刻切断。最初隐藏也是淡出，
于是 autoHide 模式下"竖条 0→1"和"把手 1→0"会同时进行 —— 那 150ms 里两块
都半透明地摆在屏幕上，细把手正好压在竖条中间，看起来就是两个侧边栏叠在一起。
瞬隐之后任何时刻只可能有一块在过渡。

**可见性只有一个所有者。** 三块 surface 各自只有一个"目标不透明度"，
由一个 16ms 的节拍器统一推进，并且每次光标轮询都重新声明一次目标值。
早期版本是每次 `setVisible` 各起一个 `setInterval` 且从不取消上一个 —— 显示和隐藏
各跑各的，最后谁写谁赢，表现就是悬停后移开、卡片或把手留在屏幕上。目标值模型下
这种竞争不可能发生，且任何一次漂移都会被下一轮轮询拉回来。

节拍器读的是 `win.getOpacity()` 而不是内部影子值：影子一旦和窗口真实值错开
（重建、外部设置），节拍器会以为"已经收好了"而停下，那块就永远留在屏幕上。

**不抢焦点、不进任务栏、不出现在 Alt-Tab。** `focusable: false` + `skipTaskbar` +
`showInactive()` + `type: 'toolbar'`（`WS_EX_TOOLWINDOW`）+ `setAlwaysOnTop('pop-up-menu')`，
每次显示后重新断言一次（Electron 的浮动层级会被非置顶任务栏挤掉）。

**数据刷新不打断动画。** 数字滚动用「快照 + 重放」：渲染前 `capture()` 量下每个字形的位置/透明度/模糊，
渲染后 `play()` 从旧位置滚到新位置。轮询每 60s 重建一次卡片，`PS 4 → 5` 是滚上去的，不是闪一下。

## 动效与材质

`motion-lab.html` 是这块的独立实验台，双击就能在浏览器里看（弹簧曲线 + 数字滚动 + rail 形状）。

- `src/motion/spring.js` — 二阶阻尼弹簧 → WAAPI 关键帧。四条通道（位置/不透明度/锐化/离场模糊）
  各自一组阻尼和周期，用自适应细分采样（49 帧里保留约 27 帧，误差 ≤0.002）
- `src/motion/roll.js` — 数字滚动的快照/重放协议

**磨砂材质**：Windows 上真亚克力要原生实现 —— Electron 透明窗里的 `backdrop-filter` 模糊的是
页面自己的合成层，不是桌面；`backgroundMaterial: 'acrylic'` 是 HWND 级的，跟不上凹形轮廓。

所以加了一个原生 helper（`src/windows-dock/`，用系统自带 `csc.exe` 编译，不需要装 SDK）：
一个 `WS_EX_NOACTIVATE|TOOLWINDOW|TRANSPARENT` 的底层窗口，贴在内容窗口正下方，
`Compositor.CreateHostBackdropBrush()` 拿到桌面背后真正的内容，再用
`CompositionGeometricClip` 按**网页里同一份 M/L/C 命令**裁成凹形轮廓。

```bash
npm run build:backdrop   # 只需跑一次；改了 .cs 才需要重跑
```

**几何必须换算成物理像素再用。** 命令列表是 DIP，而底层 `SpriteVisual` 的尺寸是物理像素；
不换算的话裁剪轮廓会比画布小一圈（150% 缩放时小三分之一），圆角外面就漏出没被裁掉的
亚克力 —— 看起来像"一块圆角面板叠在一块矩形面板上"，而且与鼠标操作无关、从启动就在。
`shapeKey` 里带上缩放系数，换显示器/改缩放会自动重建裁剪。

不可用（非 Win11 / 没编译）时自动回落到半透明底色，功能不受影响。
设置 → 显示 → 材质 可以手动选「只用半透明底色」。

验证方法：在竖条不同高度采样，颜色会跟着背后内容变（`60,70,72` / `60,56,60` / `89,101,101`），
说明是真实透出而不是盖了一层死黑。

## 位置：直接拖，不再用滑杆

竖条**可以直接拖着走**（按下后移动超过 4px 才算拖拽，不会和点击冲突）。
**卡片正文也能拖**（按在按钮上除外，那是点击）—— 从卡片上拖等于拖整个面板。
位置存进配置的 `position: {x, y, edge}`，松手即生效。

- **吸附开**（默认）：松手时离左/右/上/下边缘 **≤ 28 DIP** 才贴上去，否则停在原地。
  这是磁吸，不是钉死 —— 拖到屏幕中间它就在中间
- **吸附关**：可以拖到任意位置，但必须完整留在工作区内 —— 撞到边界就是极限

**顶边和底边吸附都会横过来。** 贴到屏幕上边/下边之后，竖条变成一根横条，
格子排成一行（左右滚动），环和编号的排法不变；
顶边时卡片从横条**下方**弹出、尾巴朝上，底边时卡片在横条**上方**、尾巴朝下，
两种情况尾巴都对准被悬停的那一格。

**底边有两个吸附位，松手时看面板下沿落在哪儿：**

| 松手时下沿 | 吸附目标 | 结果 |
|---|---|---|
| 屏幕底、或者已经压进任务栏那一条（> 上沿 2px） | 屏幕底 | 横条压在任务栏上 |
| 任务栏上沿往上 28px 以内 | 任务栏上沿 | 横条压在任务栏**之上**，不挡图标 |
| 其它 | 不吸 | 保持竖排/悬空 |

选屏幕底是因为"在任务栏之间"时贴底才像从屏幕边上长出来；面板是置顶窗口，会画在任务栏上面。
代价：压任务栏的时候，横条盖住的那几个任务栏图标点不到（光标不在横条上时窗口是穿透的）。

**拖拽按"光标在面板里占几分之几"定位，不是按左上角位移。** 所以：
- 从吸附脱离时，光标在面板上的位置不变，跟手是 1:1，不会"拖一段才开始动"；
- 横竖翻转时长宽互换，这个比例重新套上去 —— **拖的是第二格，转过来光标还压着第二格**；
- 被屏幕边界夹住时（限位优先），锚点会校正成实际位置，不会出现"光标走了面板不动"。
角上（顶部/底部 + 侧边同时贴合）按侧边处理，保持竖排 —— 不然拖到右上角、右下角会莫名翻转。

拖动过程中轴向也是**实时**的：贴着顶边或底边就横排，离开就转竖排。以前要锁住是因为
翻转会让窗口尺寸跳变，现在有 200ms 形变兜着 —— 从顶部拖下来时面板会边转边变成竖条。

**形状和留白都会跟着状态变**：

| | 轮廓 | 两端留白 | 尺寸（2 格） | 圆角 |
|---|---|---|---|---|
| 左右贴边 | 带凹肩 | 28px（凹肩要空间） | 64 × 206 | 内角 26 |
| 顶部贴边 | 带凹肩（转置） | 28px | 206 × 64 | 内角 26 |
| 底部贴边 | 带凹肩（上下翻） | 28px | 206 × 64 | 内角 26 |
| 悬空 | 四角圆角 | 2px | 64 × 154 | 26 |

凹肩只在贴边时才成立，悬空还留 28px 就成了两块空白。横排的形状是竖排那份转出来的：
顶边用旋转 `(x, y) → (y, across - x)`，底边用上下翻转 `(x, y) → (y, x)` ——
所以凹肩、圆角、卡片尾巴三处只有一份代码。
（底边不能转 180°：那样凹肩会跑到下面，看起来像"挂"在屏幕上，而不是从上边沿长出来。）

**拖离边缘时就变形，不等松手。** 松手那一下变太晚 —— 手已经离开边缘了，形状还是凹肩的。

两套轮廓刻意写成**同一套骨架**（`M L C L C L C L C Z`，每条命令点数一致，顺序是
上边→右上角→右边→右下角→下边→左下角→左边→左上角），所以可以**逐点插值**：
`p(t) = p_attached + (p_floating - p_attached) × t`，200ms 三段缓出。
不需要重采样、不会中途打结，窗口尺寸和两端留白同时过渡。
`tests/shapes.test.js` 盯着这条约束 —— 谁改了形状忘了另一边，测试先炸。

**横排↔竖排也用这套插值**：顶边形态是竖排形态转置（旋转 90°）来的、底边是上下翻过来的，
两边骨架同序，所以插出来的中间帧正好是一根**边转边变形**的斜条，看起来像面板自己转了过来。
试过把两套轮廓按弧长重采样再插值，顶部会拧出一个尖角 —— 骨架插值才是对的。

拖动中"贴不贴边""横排还是竖排"都跟实时位置走（松手才结算落盘值），
所以从顶部拖下来当场就开始转，拖回顶边又横过去。

**自动定位**（`position: null`）落在右边缘、垂直居中。

**可以跨屏拖。** 位置、夹取、磁吸、卡片位置全部按**竖条当前所在的显示器**算
（`screen.getDisplayNearestPoint`），不是主屏 —— 否则拖到副屏会被夹回来。
副屏掉线时按最近的显示器兜底。

两个实现细节：

1. **看门狗**：拖动时窗口跟着光标走，撞到边界后光标会脱离窗口，`mouseup` 就收不到了。
   所以超过 1.2 秒没移动就认定拖拽结束，避免面板一直跟着鼠标跑
2. **拖动后 200ms 内不响应点击**，否则松手会误触发"在 Gerrit 打开"

## 只看最近 N 天

默认只显示**最近 14 天**有更新的改动。实现方式不是前端过滤，而是写进查询里：

```
q:owner:self status:open    →    owner:self status:open after:2026-11-10
```

用 `after:YYYY-MM-DD`（各版本 Gerrit 都认），用户自己在查询里写了
`after:` / `before:` / `age:` 的不再加，免得把自定义条件顶掉。

实测（Gerrit 3.12.2，`recentDays=14`）：

```
[poll] owner:self status:open after:2026-11-10  → 1 条    （不加过滤时 33 条）
[poll] reviewer:self is:open  after:2026-11-10  → 0 条
```

每次轮询都会把实际执行的查询和返回条数写进 `data/app.log`，方便确认这条设置在起什么作用。

## 配置导入导出

设置 → 高级 → **导出配置 / 导入配置**。

**导出的文件不含任何凭据**（Gerrit 密码、Jenkins Token 一律不进文件），换机器导入后
重填一次即可。导入时文件里即使带了凭据字段也会被丢弃，已存的凭据保持不变。

设置窗标题栏会显示 `v0.1.0 · 12:56 启动` —— **如果你看到的时刻不是你刚启动的时间，
说明屏幕上那个还是旧实例**（单实例锁会让新启动的进程直接退出）。

**显示类设置改动即时生效**：模式 / 吸附 / 排序 / 背景不透明度 / 设置窗不透明度 / 材质
都在拖动时立刻应用到悬浮层，方便对着看效果；点「保存」才写配置，直接关窗还原。

实测（白底背景，采样纯玻璃区域）：

| 背景不透明度 | 竖条玻璃 RGB | 理论值 |
|---|---|---|
| 0% | 几乎全透，白底透上来 |
| 100% | 实心玻璃（完全不透明） |

竖条与卡片用同一个值；亚克力底层也跟着同一个值缩放。

透明度映射：**线性** `alpha = 百分比 / 100`。100% 就是完全不透明，0% 就是全透。

**设置窗的不透明度是独立的值**（`settingsAlpha`，默认 92%），不和悬浮层绑定 ——
两者层数不同（悬浮层是 tint + 亚克力两层），绑在一起怎么调都会有一边不对。
各自一个滑杆，各自一个值，最省心。

实测 DOM 值：`settingsAlpha=100 → rgb(20,24,30)`（无 alpha 通道 = 完全不透明），
`20 → rgba(20,24,30,0.2)`。

**这个值同时驱动两层**：网页里的 tint（CSS `--glass-opacity`）和原生亚克力底层的
`setOpacity`。只改前者的话，开着亚克力时滑杆会"看起来没反应" —— 因为后面那层
原生材质是独立于网页渲染的，必须单独跟着调。

## 出问题时怎么办

按 **Ctrl+Alt+D**（或托盘菜单「保存诊断快照」）：

1. 把指针判定结果和三块 surface 的真实状态写进 `data/app.log`：
   ```
   [diagnose] pointer={"point":{"x":1246,"y":200},"revealed":true,"focused":2,
     "cardVisible":true,"inRail":true,"inCard":false,"inCorridor":false}
   ```
   ```json
   [{"name":"rail","visible":true,"opacity":1,"target":1,"bounds":{...}},
    {"name":"card","visible":false,"opacity":0,"target":0,"bounds":{...}}]
   ```
2. 截一张主屏到 `data/diagnose-<时间戳>.png`
3. 附上最近 40 条可见性变更历史（`[trace]` 行），能直接看到是**谁**把面板显示出来的

"桌面多出一块面板"这类现象靠这两样基本能直接定位到是哪块 surface 没收起。

另有一层兜底：某块 surface 目标透明度是 0、却停在 0.02 以上超过 1 秒时，
会被强制收掉并记一条 `该隐藏却停在 opacity=…` 的警告。

诊断里还有一行 `allWindows`，列出进程内**所有** BrowserWindow：

```
[diagnose] allWindows=[{owned:true,visible:true,opacity:1,位置…},…]
```

正常是 3 个（rail / handle / card）+ 可能存在的设置窗。`owned=false` 的窗口就是
孤儿 —— 不受 dock 管理、会一直停在屏幕上。看到这个数字超过 4 就说明有窗口泄漏。

## 锁屏 / 休眠时

**进程照常跑**：锁屏不是休眠，定时器不会停 —— Gerrit 轮询、Jenkins 状态、构建失败自动下日志
全都继续（`build_log/` 里照常攒文件，解锁就有）。

**微信那条链必然失败**：锁屏是另一个安全桌面，任何窗口都激活不了，模拟点击也落空。
所以锁屏期间**直接丢弃**待发的微信消息（不补发 —— 解锁后收到一条半小时前的"构建失败"
只会让人误会），日志里有 `[power] 已锁屏…（丢掉 N 条待发）`。锁屏前挂着的那条重试链也作废。

**设置 → 高级 →「阻止休眠、息屏和自动锁屏」，默认就是开的**（`keepAwake`）。它做两件事，
因为 Windows 的两个机制不是一回事：

| 手段 | 挡住什么 | 怎么验 |
|---|---|---|
| 电源请求 `prevent-display-sleep` | 屏幕自动关、系统自动睡、屏保启动 | `powercfg /requests` 的 DISPLAY 栏里有 electron.exe |
| 闲置时动一下鼠标（1px 再移回来） | **闲置锁屏**：安全策略 `Interactive logon: Machine inactivity limit`（注册表 `InactivityTimeoutSecs`） | 日志 `[power] 闲置 40s，动一下鼠标防止锁屏` |

第一件就是**视频播放器/浏览器用的那一套**（它们调 `SetThreadExecutionState` 带
`ES_DISPLAY_REQUIRED`，Electron 的 `prevent-display-sleep` 是同一个东西）—— 所以"放视频不锁屏"
没什么可额外参考的，我们已经在用。

第二件只在**真有那条策略时**才做：启动时读一次 `InactivityTimeoutSecs`，为 0 就不碰鼠标
（光靠电源请求足够）。那套策略**只看有没有用户输入**，电源请求对它无效。所以人离开超过 40 秒后，
每 20 秒轻轻动一下鼠标（人一回来就停）。实测动完之后 `getSystemIdleTime()` 从 0 重新计数，
说明闲置计时器确实被重置了。

**仍然挡不住 `Win+L`**。代价：显示器一直亮着（笔记本耗电）、人不在时机器保持解锁 ——
公司有强制锁屏规定的话别开。

**休眠 ≠ 锁屏**：休眠时所有定时器一起停，醒来后集中触发一次 —— 那一次轮询会把睡眠期间
的变化一次性报出来（包括微信在醒来后发），日志里有 `[power] 系统休眠 / 唤醒`。

## 已知限制

- 只读：不能在浮层里打分/提交，点开是浏览器
- 位置按 DIP 坐标记一套，跟着竖条所在的显示器走；显示器掉线时回落到最近的
- 拖动可以从竖条或卡片正文开始（按在按钮上除外）；吸附关掉后要求面板**完整留在工作区内**
  （撞边界就是极限，不会出现"只剩一条边在屏内"的情况）
- 认证：HTTP password 或复用 `~/.gitcookies` 的 SSO 会话；内嵌登录窗还没做
- 自动检测只读非敏感信息 —— 密码/cookie 必须用户显式选择
